# A poisoned-data RL environment with a verifier built to resist reward hacking

A containerized agentic-evaluation task in the Harbor / Terminal-Bench format. An agent is
given four training corpora, told that three of them have been tampered with, and asked to
do three things: build its own poisoning attack under a strict budget, recover
classification accuracy on the three corrupted corpora, and hand back a per-row *trust
weight* saying which rows it thinks were tampered with. The weights, not the predictions,
are the deliverable that makes the task hard to fake.

| | |
|---|---|
| **Verifier** | 25 checks, binary reward, no partial credit |
| **Oracle** | 6/6 on a Modal T4, reward 1.0, identical metrics every run |
| **No-op agent** | reward 0.0 (2 checks pass, 23 error) |
| **Adversarial solutions** | 17 written, 17 rejected |
| **Reward-hacking vectors defended** | 11, each with a named mitigation and a test |
| **Threshold calibration** | 20 oracle runs across 3 GPU models |
| **Oracle runtime** | 39.0–43.4 s (T4), verifier 12.4–15.3 s |
| **Resources** | 1 GPU (T4), 8 CPU, 16 GB, no network |
| **Platforms** | image builds on arm64 and amd64; graded runs on amd64 + T4 |

The interesting part is section 5. Everything else is scaffolding around it.

## 1. What the task is, and why it is not easy for an agent

Data poisoning is a real failure mode with an awkward property: the damage is done at
training time, and by the time you notice, you have a model and a corpus and no clean
reference to diff against. The practical question is not "is this corpus poisoned" but
"which rows do I stop trusting", and that is a per-row credit-assignment problem over
thousands of rows with no labels for the thing you are trying to detect.

Three things make this hard to shortcut.

**The three corpora are poisoned three different ways, and the cheap detectors disagree
about them.** One corpus has a systematic label rotation applied to the rows the model was
surest about. One has clean-label drift: labels untouched, features moved into another
class's region, so nothing is mislabelled and per-row loss looks ordinary. One has a
spurious-direction trigger stamped onto a subset of rows that are then relabelled, so each
row is individually plausible and only the correlation between them is a lie. Measured
below: a training-loss filter is three times better on the second corpus than the third,
and gradient alignment is the other way round. An agent that finds one heuristic and
applies it everywhere clears some corpora and not others.

**The deliverable is a diagnosis, not an answer.** Predictions alone cannot pass. The agent
must ship a weight per training row, and those weights are scored by whether they rank the
tampered rows below the clean ones. Handing back uniform weights, or any constant, scores
exactly 0.5 against a 0.47 bar and fails — so "train a robust model and emit plausible
weights afterwards" does not work unless the weights genuinely carry the signal.

**It has to attack as well as defend.** Before the repair work, the agent has to poison a
clean corpus itself, inside an 8% row budget and a 0.75 per-feature cap, and actually cost
a fixed victim model accuracy on rows it has never seen. Random relabelling inside the same
budget moves the victim about 0.005; the bar is 0.04.

## 2. Task specification

The full text given to the agent is [`instruction.md`](instruction.md). In brief, it must
produce, under `/app/results/`:

- `attack/poisoned_train_x.npy`, `attack/poisoned_train_y.npy` — a poisoned copy of the
  clean corpus, at most 8% of rows changed, no feature moved more than 0.75.
- `defense/<corpus>/weights.npy` — a non-negative trust weight per training row.
- `defense/<corpus>/pred.npy`, `defense/<corpus>/val_pred.npy` — class predictions for the
  withheld rows and for the validation rows.
- `defense/<corpus>/model.pt` — `{"state_dict": ..., "logits": ...}` saved from the GPU
  without moving to CPU first.
- `ablation/<variant>/pred.npy`, `ablation/<variant>/val_pred.npy` — at least four
  variants, one named `full`, each dropping one term of the agent's objective.
- `metrics.json` and `report.md`.

The instruction states every threshold the verifier applies. Hiding the bar does not make a
task harder, it makes failures uninterpretable.

## 3. Environment

Base image `pytorch/pytorch:2.5.1-cuda12.4-cudnn9-runtime`, pinned by SHA256 digest rather
than tag so a retag cannot silently change the CUDA runtime under thresholds calibrated
against it. Four extra dependencies — numpy 1.26.4, scipy 1.14.1, pytest 8.3.4,
pytest-json-ctrf — installed from a `uv pip compile --generate-hashes` lockfile with
`pip install --require-hashes`.

Resources: 1 T4, 8 CPU, 16 GB RAM, `network_mode = "no-network"`. Agent timeout 2 hours,
verifier timeout 30 minutes.

**State setup.** The four corpora are synthetic, generated by
[`data/generate_corpora.py`](data/generate_corpora.py) from a single PCG64 seed: 72-bin
synthetic accelerometer spectra, five fault classes, built from class-specific resonance
peaks and harmonics buried in 1/f noise and observed through a fixed mixing matrix. Sizes
are 3000–3200 training rows, 800 validation, 1500 test per corpus.

The generated arrays are committed, and the Dockerfile copies only the public half. This is
deliberate on two counts. The generator is not in the image, because if it were, an agent
could re-run it and read the withheld labels straight out of the seed. And the arrays are
shipped as bytes rather than regenerated at build time because poison selection ranks rows
by a float64 surrogate fit, and BLAS reduction order is not guaranteed identical across CPU
microarchitectures — a build-time regeneration could disagree with the grader about which
rows were poisoned, which would be a silent scoring error rather than a loud one.

That determinism is checked rather than assumed. `./run.sh check-data` regenerates
everything and diffs against a committed manifest of SHA256 hashes, and each of the 20
GPU calibration runs regenerated the public corpora inside an amd64 container and compared
them to the manifest produced on an arm64 laptop. 20/20 matched bit-for-bit.

## 4. Verifier design

[`tests/test_outputs.py`](tests/test_outputs.py) is 25 pytest checks; the measurement
helpers are in [`tests/verifier_lib.py`](tests/verifier_lib.py). Binary reward: all 25 pass
or the reward is 0.

Two structural rules, both carried over deliberately from prior work:

**The library measures and never compares.** Every pass bar lives in
[`tests/thresholds.json`](tests/thresholds.json) and is applied by the tests. A threshold
that appears in two places drifts, and a drifted threshold is worse than a wrong one
because it still looks right.

**The verifier never imports anything from `/app`.** The agent can write anywhere in `/app`,
including to the copy of the reference model it was handed, so the verifier carries its own
implementation of the reference protocol rather than importing the agent's.

What is checked, in four groups:

*Data integrity.* The public corpora in the image hash to the committed manifest, so the
public and withheld halves cannot silently diverge. The withheld labels and the poison
index are not present anywhere in the image.

*The attack.* Row budget and per-feature perturbation cap, both recomputed from the
artifact. Labels in range. Then the verifier trains the reference model on the agent's
poisoned corpus and measures what it actually cost on withheld rows.

*The defense.* Predictions well-formed and not degenerate. Weights non-negative, finite,
and not uniform. Effective sample size floors. The rank-AUC check that the weights rank
tampered rows below clean ones, in every corpus. Held-out accuracy, and the gain over an
unweighted baseline the verifier trains itself.

*The artifacts.* Checkpoint structure and provenance, logits-to-predictions agreement,
anti-fabrication checks on the logits, per-corpus checkpoint distinctness, ablation variant
count and distinctness, and the recomputation of every reported accuracy from the
predictions the agent shipped alongside it.

### Why the scoring metrics are shaped the way they are

**Rank AUC rather than a weight ratio.** The structure-recovery check ranks the training
rows by the weight the agent gave them and asks how often a poisoned row outranks a clean
one. Ranks rather than raw weights because comparing group mean weights is meaningless once
a learner shrinks everything toward zero, and a survival threshold has the same problem
from the other side. Ranks are scale-free, so multiplying every weight by a constant leaves
the number unchanged; ties take average ranks, which is what makes a uniform vector score
exactly 0.5 rather than something accidentally favourable.

**Worst corpus, not the mean.** Averaging the rank AUC would let one well-diagnosed corpus
carry two that were handed back untouched. The instruction promises a per-corpus bar and the
verifier enforces a per-corpus bar.

**Effective sample size rather than a count of non-zero weights.** This one replaced a
metric that was structurally unable to fail. The natural analogue from the source design
counts surviving non-zero entries — but weights here are a sigmoid, so every weight is
strictly positive, the count is always *n*, and the gate passes by construction for any
agent whose weights are a smooth function of a score. `ESS = (Σw)² / Σw²` is scale-free the
same way the rank AUC is, is not inflated by handing discarded rows a token epsilon, and
actually measures the thing the gate is for: how many rows the weighting is really training
on.

## 5. Reward-hacking defenses

Each vector below has a specific mitigation and at least one adversarial solution in
[`scripts/adversarial.py`](scripts/adversarial.py) that exercises it. All 17 are rejected;
`./run.sh adversarial` reproduces the table.

| # | Vector | Mitigation | Caught by |
|---|---|---|---|
| 1 | Hardcode the answers by reading held-out labels | Withheld labels and poison indices live only in `tests/hidden/`, which the Dockerfile never copies; the generator that could re-derive them from the seed is not in the image either | `test_held_out_labels_are_not_in_the_container` |
| 2 | Emit uniform or constant weights and let the accuracy gate carry it | Explicit non-uniformity guard, plus a rank AUC that scores a tied vector at exactly 0.5 against a 0.47 bar | `read_weights`, `test_weights_rank_tampered_rows_below_clean_ones` |
| 3 | Rescale the weights to look like work | Rank-based metric is invariant to any monotone rescaling, so this changes nothing rather than helping | same |
| 4 | Zero almost everything so the ranking test passes for free | Effective-sample-size floors on all rows (25%) and on clean rows alone (10%) | `test_weights_retain_a_usable_training_set`, `..._the_untampered_rows` |
| 5 | Report accuracies a better run would have produced | Every reported accuracy is recomputed from the `val_pred.npy` shipped alongside it, tolerance 0.05; the reported row count is recomputed exactly from the attack artifact | `test_reported_accuracies_match_the_submitted_artifacts`, `test_reported_row_count_matches_the_attack_artifact` |
| 6 | Ship predictions the shipped model did not produce | Checkpoint logits must reproduce `pred.npy` at ≥ 0.999 | `test_checkpoint_logits_match_submitted_predictions` |
| 7 | Fabricate a logits tensor backwards from an answer vector | Structural checks a hand-built tensor fails: top-two margins must vary across rows, row spread must vary, and the non-predicted classes must not be mutually identical | `test_checkpoint_logits_are_not_fabricated` |
| 8 | Submit one trained model for all three corpora | Content fingerprint of each `state_dict`; all three must differ | `test_checkpoints_differ_between_corpora` |
| 9 | Ship a checkpoint that was never trained | Parameter count floor, all-finite, and non-degenerate variance across parameter tensors | `test_checkpoint_holds_a_real_trained_model` |
| 10 | Claim GPU work that never happened | `torch.load` without `map_location`, so tensors return on the device they were saved from; parameters and logits must be CUDA and must survive a finite CUDA backward | `test_checkpoint_was_saved_from_a_cuda_device`, `..._support_a_cuda_backward` |
| 11 | Fake the ablation by copying one result | At least four variants, at least three distinct prediction vectors by byte comparison, and `metrics.json` keys must match the variant directories | `test_ablation_*` |

Two more that are gates on effort rather than on honesty: a random relabelling inside the
attack budget is rejected because the verifier trains the victim itself and measures the
real cost, and a padded `report.md` is rejected by minimum length, required topic coverage
and a floor on how many actual numbers it cites.

### What is still open, precisely

**The checkpoint proves less than it looks like it proves.** It is evidence of a trained
model, on a CUDA device, whose logits are consistent with the submitted predictions. It is
not proof that the shipped logits were produced by that specific `state_dict`. Closing that
would mean instantiating the agent's model class and running it, which means the verifier
importing the agent's code and dictating the architecture — and the entire point of this
task is that the agent chooses its own defense. A gate that constrains the solution shape is
worse than a gate with a stated hole. The oracle itself relies on this: it ensembles three
seeds, so its logits are a mean across three models while its `state_dict` is the best
single one. That is legitimate, and any rule strict enough to forbid the fake would forbid
the ensemble too.

**CUDA provenance is provenance of the tensor, not of the computation.** A model trained on
CPU and moved to CUDA immediately before saving would pass. The run has a GPU and a two-hour
budget, so there is nothing to gain from it, but the check does not exclude it.

**A competent simple method passes, and that is intended.** The combined detector below
clears the rank-AUC bar on all three corpora. The verifier's job is to reject shortcuts, not
to be unbeatable by honest work.

**No-op agent** (verifier run against an empty results tree): reward 0.0, 2 checks pass,

**Adversarial solutions**: 17 written, 17 rejected. Full table from `./run.sh adversarial`.

**Threshold calibration** — 20 oracle runs, 12 on T4, 4 on L4, 4 on A10G, each scored
against the withheld labels:

| metric | min | max | spread | gate | headroom |
|---|---|---|---|---|---|
| mean accuracy | 0.8307 | 0.8349 | 0.0042 | 0.80 | 0.031 (~7× spread) |
| gain over baseline | 0.0444 | 0.0483 | 0.0039 | 0.02 | 0.024 (~6× spread) |
| attack accuracy drop | 0.0656 | 0.0742 | 0.0087 | 0.04 | 0.026 (~3× spread) |
| worst rank AUC | 0.1566 | 0.1803 | 0.0237 | ≤ 0.47 | large |
| min ESS fraction | 0.7938 | 0.8167 | 0.0228 | ≥ 0.25 | large |

Within a single GPU model the oracle is exactly reproducible: all 12 T4 runs agreed on
every metric to four decimals. The spread above is entirely between GPU models. Gates are
set below the observed minimum by a stated multiple of that spread, not rounded to tidy
numbers — 0.80 is the accuracy gate because the floor is 0.8307, and `attack_min_accuracy_drop`
is 0.04 rather than 0.05 because that metric has the widest cross-GPU spread and 0.04 still
sits an order of magnitude above the ~0.005 a random relabelling achieves.

**Poison damage and defense headroom** (3-seed reference model, measured on CPU):

| corpus | mechanism | rate | as shipped | poisoned rows dropped | headroom |
|---|---|---|---|---|---|
| `alpha_feed` | systematic label rotation | 16% | 0.7487 | 0.8716 | +0.123 |
| `beta_feed` | clean-label centroid drift | 30% | 0.7989 | 0.8224 | +0.024 |
| `gamma_feed` | spurious-direction trigger | 18% | 0.8013 | 0.8578 | +0.056 |

**Detector visibility** — rank AUC per detector, from `./run.sh detectability`:

| corpus | training loss | kNN label agreement | validation-gradient alignment | all three |
|---|---|---|---|---|
| `alpha_feed` | 0.151 | 0.273 | 0.153 | 0.063 |
| `beta_feed` | 0.079 | 0.154 | 0.188 | 0.060 |
| `gamma_feed` | 0.266 | 0.372 | **0.039** | 0.236 |

`gamma_feed` is the corpus where the loss filter and the neighbourhood test are weakest and
gradient alignment is by far the strongest; `beta_feed` is where gradient alignment is
weakest. That ordering is the reason the ablation is informative.

**Runtime and hardware.** The oracle takes 39–43 s on a T4 under `solve.sh`. On the same
Modal image with no GPU attached it takes 88–94 s, so the GPU is worth about 2.3× here. On
a local Apple-silicon laptop it takes 17.8 s — faster than the T4. **The GPU requirement is
not justified by speed.** It exists because the checkpoint-provenance defense (vector 10)
requires CUDA tensors to be meaningful. That is stated plainly rather than dressed up: the
model is a small full-batch MLP and kernel-launch overhead dominates.

**What was not measured.** No agent has been run against this task — the oracle and the
adversarial bundles are the only solutions that exist, so there is no pass rate for any
model and none is claimed. Cross-GPU spread was measured on three models (T4, L4, A10G);
nothing is claimed about H100 or others. The image was built on arm64 locally (with the
amd64 base under emulation) and on amd64 in CI; graded runs are amd64 + T4.

## 7. Quickstart

```bash
git clone <repo-url> && cd <repo>

# everything that runs without a GPU: regenerate and hash-check the corpora, build the
# image, run the oracle on CPU, run the verifier, run all 17 adversarial solutions
./run.sh cpu-suite

# individually
./run.sh check-data          # corpora reproduce from the seed
./run.sh build               # docker build of the task image
./run.sh oracle --allow-cpu  # authoring-only CPU run; cannot pass the CUDA checks
./run.sh verify              # verifier against ./results
./run.sh adversarial         # 17 shortcuts, all should be rejected
./run.sh detectability       # per-detector visibility of each poison
./run.sh parity              # Modal image definitions still match the Dockerfile
```

With a GPU, `./run.sh oracle` runs the real path and `./run.sh verify` runs all 25 checks
including the two CUDA-only ones. Without one, those two skip and the other 23 run.

To reproduce the GPU numbers on Modal:

```bash
pip install modal && modal setup
modal deploy scripts/modal_calibrate.py
python - <<'PY'
import modal
f = modal.Function.from_name("poisoned-corpus-calibrate", "validate")
for i in range(6): f.spawn(i, False)
f.spawn(0, True)   # the no-op agent
PY
python scripts/modal_calibrate.py --collect
```

The harness deploys and spawns rather than using `modal run`, and results land in a
`modal.Dict`. That is not stylistic: from the network this was authored on, long silent
calls lose their gRPC stream and multi-megabyte image uploads fail outright, so the corpora
are regenerated inside the image from the seed instead of uploaded — which is also what
turns the upload into the amd64 determinism check described in section 3.

## 8. Design notes

**Three findings that changed the design.** These are here because they are worth more than
the code.

*My first defense was confidently backwards, and the metric caught it.* The initial
trust learner scored a rank AUC of 0.847 — it was ranking poisoned rows as the **most**
trustworthy, because the gradient-alignment term had its sign inverted. Accuracy dropped
0.095 below the unweighted baseline. That is the strongest evidence I have that the ranking
metric measures something real: it detected a defense that was not merely weak but exactly
inverted, and it did so before any human read the code.

*Feature perturbation makes the attack weaker, not stronger.* The attack budget permits a
0.75 per-feature step, and the obvious move is to use it. Measured, the label flip alone
costs the victim 0.075; adding a dense signed step of 0.35 drops that to 0.017 and 0.70
drops it to 0.001 — and it is worse in **both** directions, toward the false label and away
from it. A dense step across 72 standardized features turns a poisoned row into an outlier
far off the data manifold, which the victim then discounts. The oracle therefore spends none
of its perturbation budget. The cap stays in the specification and the verifier still
enforces it, because an agent may find a better use for it than I did.

*Clean-label poisoning is weak on aggregate accuracy, and that shaped the gate.*
`beta_feed` needed a 30% poison rate to move accuracy 2.4 points, where the label-rotation
corpus moved 12.3 points at 16%. Interpolating toward a target centroid landed poisoned rows
inside the target's cloud; pushing along a logistic weight-difference direction, which was
the first thing I tried, just parked them in empty space where the model ignored them. This
is why the accuracy gate is a **mean** across three corpora rather than a per-corpus bar —
a per-corpus accuracy gate calibrated to `beta_feed` would be too loose to mean anything on
the other two. The rank-AUC gate stays per-corpus, because detectability, unlike damage, is
comparable across the three.

**Two defenses from the source design that were deliberately not carried over.** The task
this was rebuilt from drew its data from a public dataset, so it shipped a network blacklist
to stop an agent looking up the withheld labels, and a re-identification audit measuring
whether the anonymised graphs could be matched back to the source. Neither applies here: the
data is synthetic, there is no external source to look up and nothing to re-identify. Rather
than port a blacklist that guards nothing, the environment sets `network_mode = "no-network"`
— it needs no network at all, which is both simpler and stronger. A defense that is not
defending anything is worse than one fewer defense, because it implies a threat model that
does not exist.

**Known limitations.** The two open holes in section 5 are the real ones. Beyond those: the
corpora are small enough to fit in memory and the model is small enough that a GPU barely
helps, so this measures an agent's judgement about data rather than its ability to manage a
large training job. The three poisoning mechanisms are the ones I implemented; a fourth that
defeats all three detectors at once would make the task meaningfully harder and I have not
built one. The `--allow-cpu` flag on the oracle is an authoring convenience and is
deliberately unable to pass the CUDA checks, which means the CPU path validates the
verifier's logic rather than a full graded run.

**What I would extend.** A second held-out corpus with a poisoning mechanism the agent has
not seen, scored but not described in the instruction, to test whether a defense generalises
or was tuned. A budget on the agent's own wall-clock inside the container, so that
brute-forcing the weight vector against the validation split becomes expensive. And a
partial-credit variant of the reward for training signal, which the current binary reward
deliberately does not provide.
